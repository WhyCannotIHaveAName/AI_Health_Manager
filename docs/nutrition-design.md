# 饮食分析方案

## 首版流程

1. 用户输入文字或照片。照片缩放、重新编码，去除 EXIF 后才发送。
2. DeepSeek `deepseek-flash` 返回 JSON 食物列表、数据库候选编号、重量与重量范围。常见食材使用人工中文索引，提示词只包含索引对应条目，避免发送完整数据库。
3. 本地验证数据类型、重量上下界和编号。只接受本地存在的数据库编号，不采纳模型返回的营养值。
4. 以每100g的权威数据乘以可食部重量计算。不存在的食物和缺失营养字段持续保留未知状态。
5. 用户检查生熟、份量、油糖、漏项、剩余量；支持手动查找全部7,793项数据或用包装标签覆盖，确认后才保存。

包装标签目前按每100g录入，饮料按实际克数填写，不自动假定所有饮料1ml=1g。手动更改任一营养值后，来源切换为“用户标签 / 手动录入”。允许记录不完整的营养信息，但每种营养汇总均注明缺失项。

## 工作量与效果

| 方案 | 首版决策 | 原因 |
| --- | --- | --- |
| 让语言模型直接估计所有营养素 | 不采用 | 数值不可追溯，油糖、熟重与品牌误差无法检查 |
| 公开营养数据库 + 检索 + 可编辑份量 | 已实现 | 不需要训练，数值可追溯，离线仍能记录 |
| 中式标准配方库与品牌标签库 | 后续优先 | 提升本地饮食覆盖；需取得可再分发数据许可并保留配方出处 |
| 视觉模型后训练 | 暂缓 | 需要可靠标签、图片授权与对照评测；训练不能解决照片缺少尺度和隐含油量的问题 |

数据库能稳定计算数值，但数据库编号也可能被模型选错。首版界面同时显示来源和匹配编辑入口。模型提示词要求混合菜拆分主要原料、油、糖，禁止重复计算整菜和食材；实际能否遵守仍需真实样本评测。

## 验收与下一步

仓库测试验证了计算、份量边界、未知编号、缺失项、图片请求结构和异常路径。**这些不是食物识别准确率测试。** `scripts/evaluate_meals.py` 可用独立测试密钥运行文字样本并输出匹配率和重量误差；默认只做离线数据检查，`--live` 才会调用 API 计费。

正式量化识别效果前，建立至少50餐的授权样本，覆盖食堂、外卖、家庭菜、包装食品和奶茶；标注菜名、生熟、称重、剩余量及油糖。文字输入和照片输入分别统计：

- 食物项检出率、误检率、数据库编号匹配率。
- 已称重食物的重量绝对百分比误差与估计范围覆盖率。
- 有可靠配方/标签的整餐能量和蛋白质误差；未知项占比。
- 用户修正项数与完成一次记录的时间。

先修复高频别名、配方与检索问题，再对同一批样本做盲测。仅当类别识别仍稳定落后且已有独立训练集时，再评估后训练；测试集不得用于训练。首版不声称达到任何识别准确率或医学精度。
